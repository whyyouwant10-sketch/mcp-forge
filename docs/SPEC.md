# MCP Forge generator specification

**Status:** design contract
**Scope:** OpenAPI 3.x to a TypeScript MCP server skeleton
**Implementation status:** not implemented by this document

MCP Forge is a deterministic code generator. It reads one OpenAPI 3 JSON or
YAML document and writes a self-contained TypeScript project whose MCP tools
call the described HTTP operations. The generated server uses the MCP stdio
transport. Network access is always behind an injectable transport so the
generated fixture client can exercise the server without making real HTTP
requests.

## 1. Goals and non-goals

### Goals

- Accept OpenAPI 3.0 and 3.1 JSON or YAML.
- Validate the document before generating anything.
- Generate one MCP tool per eligible OpenAPI operation, with a stable name,
  input schema, output schema, and useful description.
- Preserve the operation's path, method, parameters, request body, response
  content type, and security requirements in generated metadata.
- Generate a runnable TypeScript MCP server using stdio.
- Generate a fixture-based test client using a mock transport, without network
  access.
- Produce byte-for-byte identical output for identical inputs and options.

### Non-goals for v1

- Calling remote `$ref` URLs or downloading an OpenAPI document.
- OAuth login flows, token exchange, browser interaction, or credential
  discovery.
- Generating a general-purpose REST SDK.
- Inferring undocumented behavior from examples or prose.
- Supporting WebSockets, callbacks, webhooks, or non-HTTP operations.
- Sending secrets to a model or using an LLM to author descriptions. “Auto-
  written” descriptions are deterministic templates composed from the spec.

## 2. CLI contract

The package exposes a binary named `mcp-forge`.

### Commands

```text
mcp-forge generate --input <spec.{json,yaml,yml}> --output <directory> [options]
mcp-forge validate --input <spec.{json,yaml,yml}>
mcp-forge --version
mcp-forge --help
```

`generate` is the only command that writes files. `validate` parses and
validates the complete input and prints a concise error list; it must not
create or modify the output directory.

### Options

| Option | Required | Default | Contract |
|---|---:|---|---|
| `--input`, `-i` | yes | — | Local JSON/YAML file. Must be a regular file. |
| `--output`, `-o` | yes for `generate` | — | Output directory. Created if absent; existing generated files are replaced only after validation succeeds. |
| `--name` | no | sanitized `info.title` | Project/display name used in generated metadata. |
| `--server-url` | no | first `servers[0].url`, otherwise `http://localhost` | Base URL used by the default real transport. Must be `http` or `https`; environment placeholders are preserved. |
| `--package-manager` | no | `npm` | One of `npm`, `pnpm`, or `yarn`; controls the lockfile hint and README commands only. |
| `--include-deprecated` | no | false | Include operations marked `deprecated: true`. |
| `--force` | no | false | Permit replacing an existing output directory containing a `.mcp-forge-manifest.json` generated by this tool. Never deletes unrelated directories. |
| `--strict` | no | true | Fail on unsupported constructs, ambiguous response schemas, or unsafe server URLs instead of emitting a warning. |

Unknown options, missing values, invalid enum values, and positional
arguments are errors and exit with status 2. Input/schema errors exit with
status 1. Successful validation/generation exits with status 0.

### Output and errors

- Normal output is one summary line per command, suitable for CI.
- Diagnostics go to stderr and include a JSON pointer when available, for
  example `/paths/~1pets/get/responses/200`.
- The generator must not print secrets, authorization header values, complete
  request URLs containing query values, or the full input document.
- A failed generation is atomic: write to a sibling temporary directory and
  rename it into place only after all files and the manifest are complete.

Example:

```sh
mcp-forge validate -i fixtures/pets.yaml
mcp-forge generate -i fixtures/pets.yaml -o generated/pets --name pets
```

## 3. Accepted OpenAPI input

### Required document shape

The root must be an OpenAPI 3 document:

- `openapi` must match `3.0.x` or `3.1.x`.
- `info.title` and `info.version` must be non-empty strings.
- `paths` must be an object. An empty `paths` object is valid but produces a
  server with no tools and a validation warning.
- Each operation must have a supported HTTP method: `get`, `post`, `put`,
  `patch`, or `delete`. `head`, `options`, `trace`, and path-item `$ref`
  entries are rejected in strict mode.
- Every included operation must have at least one successful response in the
  `2xx` range or `default`; otherwise it is skipped with a warning in lenient
  mode and is an error in strict mode.

The parser may accept YAML 1.2, JSON, comments, and YAML anchors, but the
normalized internal model must not retain YAML-specific ordering or aliases.
Duplicate mapping keys are errors.

### `$ref` policy

Only local JSON Pointers beginning with `#/` are supported in v1. References
are resolved against the parsed document, cycles are rejected, and the
resolved value is deep-cloned before normalization. External files and URLs
are rejected, including references hidden in an external reference chain.

The resolver must detect and report a cycle with the complete reference
chain. A `$ref` with sibling fields follows OpenAPI 3.1 semantics only when
the input declares 3.1; for 3.0 it is treated as an error rather than silently
merging fields.

### Supported operation data

The generator consumes:

- `operationId`, `summary`, `description`, `deprecated`, and `tags`.
- Path, query, header, and cookie parameters, including path-level
  parameters. Path parameters are always required.
- `requestBody` content for JSON and `application/x-www-form-urlencoded`.
  Multipart and binary bodies are unsupported in strict mode.
- Response content for JSON and text. A response with no content is modeled
  as `undefined`.
- `components.schemas`, including objects, arrays, enums, nullable values,
  required fields, defaults, descriptions, and bounded scalar constraints.
- `securitySchemes` of type `apiKey` (header/query), `http` bearer, and
  `http` basic. `oauth2` and `openIdConnect` are represented as unsupported
  security metadata and fail strict generation.

Unsupported schema keywords are retained in a generated comment only when
they do not change runtime validation. The generator must not claim to
enforce constraints it cannot emit.

## 4. Generated project layout

Generation creates exactly this layout (plus any package-manager lockfile
chosen by a future implementation):

```text
<output>/
├── .mcp-forge-manifest.json
├── README.md
├── package.json
├── tsconfig.json
├── src/
│   ├── index.ts
│   ├── server.ts
│   ├── generated-tools.ts
│   ├── generated-types.ts
│   ├── transport.ts
│   └── http/
│       ├── request.ts
│       └── real-transport.ts
└── test/
    ├── fixture-client.ts
    └── fixtures.ts
```

### Required generated behavior

`src/index.ts`:

- Creates the default `RealHttpTransport` from environment configuration.
- Creates the MCP server and connects `StdioServerTransport`.
- Does not log to stdout. Human-readable logs go to stderr.
- Handles SIGINT/SIGTERM by closing the MCP transport and exiting cleanly.

`src/server.ts`:

- Exports `createServer(deps)` for tests and `createStdioServer(deps)` for
  production startup.
- Registers every generated tool with its tool name, description, input
  schema, and handler.
- Accepts an injected `HttpTransport`; no tool handler imports `fetch`, an
  HTTP library, filesystem APIs, or environment access directly.

`src/generated-tools.ts`:

- Contains a deterministic `ToolDefinition[]` in normalized operation order.
- Builds the MCP input schema from the operation's parameters and request
  body.
- Converts tool input into an `HttpRequest` and delegates it to the injected
  transport.
- Validates and normalizes the response before returning MCP content.
- Exposes no mutable global state.

`src/generated-types.ts`:

- Contains named TypeScript types for reusable schemas and operation input /
  output types.
- Is generated only from the normalized model, never from source formatting.

`src/transport.ts`:

```ts
export type HttpRequest = {
  method: "GET" | "POST" | "PUT" | "PATCH" | "DELETE";
  url: string;
  headers: Record<string, string>;
  body?: string;
};

export type HttpResponse = {
  status: number;
  headers: Record<string, string>;
  body?: string;
};

export interface HttpTransport {
  send(request: HttpRequest): Promise<HttpResponse>;
}
```

`src/http/real-transport.ts` is the only generated implementation that may
call `fetch`. It reads the base URL and credentials from documented
environment variables, applies a timeout, and returns a bounded response.

`test/fixture-client.ts` creates the generated MCP server with a
`FixtureTransport`. It invokes each fixture tool through the same MCP-facing
handler path as production, asserts the expected request and response, and
exits non-zero on failure. It must not import or mock the global `fetch`.

### Manifest

`.mcp-forge-manifest.json` records the generator version, normalized input
SHA-256, OpenAPI version, project name, selected operations, and generator
options. It must not contain credentials, resolved secret values, or the full
source document. Keys are sorted and the file ends with one newline.

## 5. Tool model and descriptions

### Operation ordering

Operations are sorted by the tuple `(toolName, method, path)` using Unicode
code-point ordering. Source map order, YAML order, and filesystem traversal
must never affect output.

### Tool names

The name is derived in this order:

1. `operationId`, if present.
2. `<method>_<path-with-parameters>`, if absent.

Normalization rules are applied after derivation:

- Convert camelCase, spaces, punctuation, and path separators to word
  boundaries; preserve ASCII letters and digits.
- Lowercase and join words with `_`.
- Replace `{id}` with `by_id` (so `get_/pets/{petId}` becomes
  `get_pets_by_pet_id`).
- Prefix `tool_` if the first character is a digit.
- Truncate to 64 characters at a word boundary, then append a stable
  8-character lowercase base32 suffix of SHA-256(path + `:` + method + `:` +
  original operationId) when truncation or collision occurs.
- If two operations still collide, append `_2`, `_3`, and so on in sorted
  operation order.
- Reject names that equal a reserved MCP/runtime name (`initialize`,
  `notifications/initialized`, `list_tools`, `call_tool`, or names beginning
  with `__`).

The original operationId and path remain in generated metadata so a user can
trace a tool back to the source operation.

### Input schema

Each tool accepts one top-level object. Parameter locations are represented by
stable keys:

```ts
{
  path?: { /* path parameters */ },
  query?: { /* query parameters */ },
  headers?: { /* header parameters */ },
  cookies?: { /* cookie parameters */ },
  body?: { /* request body */ }
}
```

Only required sections/fields are required. A single required body is exposed
as `body`; parameters remain grouped by location to prevent accidental header
or query injection. OpenAPI `style` and `explode` are implemented only for
the standard combinations of each supported location; unsupported combinations
are strict-mode errors.

JSON Schema / OpenAPI schemas map to runtime validation schemas as follows:

| OpenAPI type | Generated runtime schema |
|---|---|
| `string` | string, with enum, pattern, min/max length when supported |
| `integer`, `number` | number, with integer and min/max constraints |
| `boolean` | boolean |
| `array` | array of the item schema, with min/max items |
| `object` | object with declared properties and required keys |
| `oneOf`, `anyOf` | union schema with branch validation |
| `allOf` | merged object schema when all branches are objects; otherwise a composed schema |
| `nullable: true` / `type: [T, "null"]` | `T` or null |

The emitted schema must reject unknown top-level input groups and unknown
fields when the OpenAPI schema has `additionalProperties: false`. It should
accept them otherwise, while still refusing prototype-pollution keys
(`__proto__`, `constructor`, and `prototype`) at every object boundary.

### Auto-written descriptions

Descriptions are generated in this priority order:

1. `description`.
2. `summary` plus a deterministic generated suffix.
3. A template from method, path, tags, and operationId.

The template is:

```text
<HTTP method> <path>. <summary-or-"Execute this operation">.
Inputs: <required input list or "none">. Returns: <best 2xx response media type or "no response body">.
<security sentence when applicable>
```

Whitespace is collapsed, control characters are removed, and descriptions are
limited to 1,024 UTF-8 bytes. The generator never invents endpoint semantics
such as “deletes permanently” unless the source description says so.

## 6. HTTP and security behavior

### Injectable transport

The generated server depends on `HttpTransport`, not on `fetch`. The default
real transport is supplied only by `src/index.ts`. Tests pass a fixture
transport that matches requests by method and URL and returns a predefined
response. A fixture mismatch is a test failure and must not fall through to
the network.

The transport boundary includes the fully resolved URL, serialized body, and
headers so request construction is testable independently of network I/O.

### URL and request limits

- Only `http` and `https` server URLs are allowed.
- `file:`, `data:`, and `javascript:` URLs are rejected. Before the real
  transport connects, IPv4 and IPv6 literals are parsed and every hostname is
  resolved with all results. Any loopback, private (RFC 1918 or IPv6 unique
  local), link-local, unspecified, or multicast result is rejected by default,
  as are the `localhost` aliases. The connection is pinned to the validated
  address to avoid a second DNS lookup and DNS rebinding between validation and
  connection; changes to OS routing or network interfaces are outside this
  process boundary. An explicit runtime opt-in may allow local development
  URLs; generation itself never makes a request. DNS lookup failures and
  invalid lookup results fail the request.
- Redirects are disabled by default; a future option may permit at most three
  redirects while re-validating each destination.
- Request body: 1 MiB maximum.
- Response body: 4 MiB maximum, measured before JSON parsing.
- Timeout: 10 seconds per request, configurable only through a bounded
  environment variable (`MCP_FORGE_TIMEOUT_MS`, 100–60,000).
- Query parameters and headers are serialized from validated input only.
- Header names are fixed by the operation and security configuration; user
  input cannot supply arbitrary header names.

### Credentials

Generated code reads only named environment variables documented in
`README.md`:

- `MCP_FORGE_API_KEY` for `apiKey` schemes.
- `MCP_FORGE_BEARER_TOKEN` for bearer schemes.
- `MCP_FORGE_BASIC_USERNAME` and `MCP_FORGE_BASIC_PASSWORD` for basic auth.

Missing credentials produce a redacted runtime error. Values never appear in
tool descriptions, fixture files, logs, error payloads, or the manifest.
Security requirements are represented as alternatives (OR) and multiple
schemes in one requirement object are applied together (AND), matching
OpenAPI semantics. Unsupported schemes fail generation in strict mode.

## 7. Determinism and reproducibility

For the same generator version, input bytes after UTF-8 decoding, and CLI
options, generation must produce identical bytes:

- Normalize line endings to LF and write a final newline in every text file.
- Sort paths, methods, schemas, properties where ordering is not semantically
  meaningful, security scheme names, generated imports, and manifest keys.
- Never include current time, absolute input/output paths, hostnames, random
  identifiers, or platform-specific separators in generated files.
- Use stable JSON serialization (two-space indentation, sorted keys) for the
  manifest and fixture data.
- Normalize the input into an intermediate representation before rendering;
  equivalent JSON/YAML formatting and mapping order should render identically.
- Generation must be offline. A test can enforce this by denying DNS/socket
  access to the generator process.

## 8. Fixture and sample

The following is the minimum fixture used in acceptance tests. It intentionally
includes a path parameter, a query parameter, a JSON body, a bearer security
scheme, and a reusable schema.

```yaml
openapi: 3.0.3
info:
  title: Pet API
  version: 1.0.0
servers:
  - url: https://api.example.test/v1
security:
  - bearerAuth: []
paths:
  /pets/{petId}:
    get:
      operationId: getPet
      summary: Get a pet
      parameters:
        - name: petId
          in: path
          required: true
          schema:
            type: string
        - name: includeOwner
          in: query
          required: false
          schema:
            type: boolean
      responses:
        '200':
          description: A pet
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Pet'
        '404':
          description: Not found
  /pets:
    post:
      operationId: createPet
      summary: Create a pet
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/NewPet'
      responses:
        '201':
          description: Created
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Pet'
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
  schemas:
    NewPet:
      type: object
      required: [name]
      properties:
        name:
          type: string
          minLength: 1
        age:
          type: integer
          minimum: 0
    Pet:
      allOf:
        - $ref: '#/components/schemas/NewPet'
        - type: object
          required: [id]
          properties:
            id:
              type: string
```

The normalized tool names for this fixture are `create_pet` and `get_pet`.
The fixture client must assert at least these calls:

```ts
await client.callTool("get_pet", {
  path: { petId: "p-1" },
  query: { includeOwner: true },
});

await client.callTool("create_pet", {
  body: { name: "Ada", age: 4 },
});
```

The mock transport must observe, without contacting the network:

```text
GET https://api.example.test/v1/pets/p-1?includeOwner=true
POST https://api.example.test/v1/pets
Authorization: Bearer <value supplied by the test dependency>
Content-Type: application/json
```

The generated fixture client should assert a `200` JSON `Pet` response for
`get_pet`, a `201` JSON `Pet` response for `create_pet`, invalid input for a
missing `petId`, and a fixture mismatch failure.

## 9. Validation and acceptance criteria

An implementation conforms to this specification when all of the following
are true:

1. `validate` accepts the sample JSON and YAML fixtures, rejects malformed
   YAML/JSON, rejects non-OpenAPI documents, and reports JSON pointers for
   invalid operations.
2. `generate` emits the complete layout above and a generated project passes
   `npm run build` (or the selected package manager's equivalent) without
   network access.
3. Running the generated `src/index.ts` connects an MCP client over stdio,
   lists `create_pet` and `get_pet`, and returns their generated descriptions
   and input schemas.
4. The generated fixture client invokes both tools through the MCP server and
   passes using only `FixtureTransport`; replacing the fixture transport with
   one that throws on `fetch` still passes.
5. The fixture client observes correctly encoded path/query parameters,
   request body, content type, and injected bearer authorization.
6. Invalid tool input is rejected before `HttpTransport.send` is called.
7. A transport failure, non-success response, malformed response JSON, and
   oversized response produce bounded, non-secret MCP errors.
8. Running generation twice with the same input and options produces identical
   file names and bytes. JSON versus YAML equivalent fixtures produce the same
   generated source except for the manifest's input-byte hash.
9. Generation never opens a socket, follows a remote `$ref`, or emits secret
   values. External refs, unsupported auth, unsafe URLs, duplicate operation
   names, and unsupported media types are covered by negative tests.
10. `--force` replaces only a directory carrying this generator's manifest;
    without it, an existing generated output is refused and unrelated files
    are preserved.

The implementation should add automated tests for each criterion before
declaring the generator ready for release. This document deliberately defines
the contract and fixtures without implementing the product.
